# Серверная часть

## Общая характеристика

Серверная часть проекта `Универ` находится в пакете `server`. Она реализует API, бизнес-логику, авторизацию, работу с базой данных, интеграцию с внешними сервисами и административные операции.

Сервер построен на Express и tRPC. Данные хранятся в PostgreSQL, доступ к ним выполняется через Prisma ORM.

Сервер является источником истины для прав доступа и состояния данных. Клиентские ограничения в интерфейсе считаются вспомогательными и не заменяют серверные проверки.

## Структура

| Путь | Назначение |
| --- | --- |
| `server/src/index.ts` | Точка входа серверного приложения. |
| `server/src/lib` | Инфраструктурные модули: env, Prisma, Redis, tRPC, Passport, logger. |
| `server/src/router` | tRPC-процедуры по функциональным областям. |
| `server/src/prisma` | Prisma-схема и миграции базы данных. |
| `server/src/emails` | MJML-шаблоны писем. |
| `server/src/test` | Общие утилиты интеграционных тестов. |
| `server/src/utils` | Вспомогательные функции. |

## Запуск приложения

При запуске `server/src/index.ts` выполняет следующие действия:

1. Создает контекст приложения.
2. Выполняет начальную подготовку данных через `presetDB`.
3. Создает Express-приложение.
4. Настраивает CORS.
5. Подключает Passport JWT.
6. Подключает tRPC API по пути `/trpc`.
7. Подключает `/trpc-playground` для разработки.
8. Регистрирует общий обработчик ошибок.
9. Запускает HTTP-сервер на порту из переменной окружения `PORT`.

## Контекст приложения

Контекст приложения объединяет инфраструктурные зависимости, необходимые бизнес-логике:

- Prisma Client;
- Redis-клиент, если задан `REDIS_URL`;
- данные текущего пользователя в контексте запроса.

В tRPC-процедурах текущий пользователь доступен как `ctx.me`.

## API-слой

API реализован как набор tRPC-процедур. Корневой роутер находится в `server/src/router/index.ts`.

Каждая процедура отвечает за отдельное действие: получение данных, создание сущности, изменение состояния или выполнение административной операции. Полный список процедур вынесен в [api.md](./api.md), чтобы не дублировать справочник API в описании серверной реализации.

Типовой серверный запрос проходит следующие этапы:

1. Express принимает HTTP-запрос.
2. Passport при наличии токена заполняет `req.user`.
3. tRPC создает контекст запроса.
4. Процедура валидирует входные данные.
5. Сервер выполняет проверку прав и бизнес-логику.
6. Prisma читает или изменяет данные в PostgreSQL.
7. Результат возвращается клиенту в типизированном формате.

## Авторизация

Авторизация реализована через JWT и Passport.

Клиент отправляет токен в заголовке:

```text
Authorization: Bearer <token>
```

Сервер:

1. Извлекает токен из заголовка.
2. Проверяет подпись через `JWT_SECRET`.
3. Получает `userId` из payload.
4. Загружает пользователя из базы данных.
5. Помещает пользователя в `req.user`.
6. Передает пользователя в tRPC-контекст как `me`.

## Права доступа

Права пользователя хранятся в поле `permissions` модели `User`. Используются значения:

- `DELETE_POST`;
- `ALL`;
- `SUPER_ADMIN`.

Вспомогательные проверки находятся в `server/src/utils/can.ts` и в общем пакете `shared`.

Примеры проверок:

- может ли пользователь удалить публикацию;
- является ли пользователь владельцем публикации;
- является ли пользователь администратором;
- является ли пользователь супер-администратором.

Права на действия в сообществах дополнительно проверяются через роли владельца и модератора.

## Работа с базой данных

База данных описана в `server/src/prisma/schema.prisma`. Prisma используется для:

- генерации типизированного клиента;
- выполнения запросов к PostgreSQL;
- управления миграциями;
- описания связей между сущностями.

Миграции хранятся в `server/src/prisma/migrations`.

## Redis

Redis используется как опциональный кэш. Если переменная окружения `REDIS_URL` не задана, сервер продолжает работать без кэширования.

Кэш реализован через:

- `server/src/lib/redis.ts` для подключения;
- `server/src/lib/cache.ts` для чтения и записи JSON-значений с TTL.

Ключи кэша формируются с префиксом `somnia:v1`.

## Cloudinary

Cloudinary используется для хранения изображений. Серверная процедура `prepareCloudinaryUpload` подготавливает параметры, необходимые клиенту для загрузки файла.

Такой подход позволяет не передавать секретные ключи Cloudinary в клиентское приложение.

## Уведомления

Сервер создает уведомления при событиях, важных для пользователя или администратора:

- лайк публикации;
- комментарий;
- ответ на комментарий;
- подписка на пользователя;
- блокировка или разблокировка в сообществе;
- новая жалоба;
- новая заявка на верификацию сообщества.

Уведомления хранятся в таблице `Notification`.

## Жалобы и администрирование

Административные процедуры позволяют:

- получать список жалоб;
- изменять статус жалобы;
- получать список заявок на верификацию;
- изменять статус заявки;
- получать список пользователей;
- назначать административные права;
- просматривать удаленные публикации.

Доступ к этим процедурам должен проверяться на сервере, так как скрытие admin-экрана на клиенте не является достаточной защитой.

## Обработка ошибок

tRPC настроен с общим форматтером ошибок. Ожидаемые ошибки представлены через специальный тип и получают признак `isExpected`.

Сервер логирует:

- успешные tRPC-запросы;
- ошибочные tRPC-запросы;
- ошибки Express;
- ошибки Redis;
- ошибки кэша.

## Email-шаблоны

В `server/src/emails` находятся MJML-шаблоны писем. При сборке они компилируются в HTML и копируются в `dist`.
