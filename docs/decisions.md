# Проектные решения

## Назначение

Раздел фиксирует ключевые технические решения проекта `Универ` и причины их выбора. Он дополняет [архитектурное описание](./architecture.md): архитектура показывает состав системы, а этот документ объясняет, почему система устроена именно так.

## Monorepo

Проект разделен на пакеты `webapp`, `server` и `shared`, но хранится в одном репозитории. Такой подход выбран из-за тесной связи клиентского и серверного кода: API, схемы входных данных и типы сущностей должны меняться согласованно.

Преимущества решения:

- один цикл разработки для клиента, сервера и общих типов;
- проще поддерживать совместимость между frontend и backend;
- можно переиспользовать схемы валидации и типы без копирования;
- сборка и проверки запускаются из корня репозитория.

Ограничение решения: при росте проекта потребуется аккуратно следить за зависимостями между пакетами, чтобы общий пакет не начал зависеть от деталей реализации клиента или сервера.

## TypeScript

TypeScript используется во всех основных пакетах. Для проекта с общим API-контрактом это снижает риск ошибок при изменении модели данных или процедуры API: несовместимые изменения становятся заметны на этапе проверки типов.

В дипломной работе это решение можно рассматривать как способ повысить сопровождаемость клиент-серверного приложения.

## tRPC вместо REST

tRPC выбран как основной механизм API, потому что проект разрабатывается на TypeScript и на клиенте, и на сервере. В такой конфигурации tRPC позволяет получать типы процедур напрямую из серверного роутера, без отдельной OpenAPI-схемы и ручного описания DTO.

Преимущества:

- типизированные вызовы API на клиенте;
- меньше дублирования контрактов;
- удобная группировка процедур по предметным областям;
- совместимость с React Query на клиенте.

Ограничение: tRPC сильнее привязывает клиент к TypeScript-экосистеме. Если в будущем потребуется публичный API для сторонних клиентов, может понадобиться отдельный REST или OpenAPI слой.

## Shared-пакет

Пакет `shared` содержит общие схемы и типы. Его задача - быть границей контракта между клиентом и сервером, а не местом для бизнес-логики.

Это решение особенно важно для форм и API: клиент может использовать те же ограничения данных, что и сервер, а сервер остается источником истины при окончательной проверке запроса.

## Prisma и PostgreSQL

PostgreSQL выбран как основное хранилище, потому что модель проекта реляционная: пользователи, публикации, комментарии, сообщества, роли, жалобы и уведомления связаны между собой множеством отношений.

Prisma используется для:

- описания схемы данных в одном месте;
- генерации типизированного клиента;
- управления миграциями;
- явного описания связей, индексов и ограничений.

Ограничение Prisma заключается в том, что сложные оптимизированные SQL-запросы иногда удобнее писать вручную. Для текущего масштаба проекта преимущества типизации и миграций важнее.

## Expo и React Native Web

Клиентская часть построена на Expo и React Native, а web-версия работает через React Native Web. Это позволяет использовать общий набор экранов и компонентов для мобильной и web-среды.

Преимущества:

- единая кодовая база интерфейса;
- общий стек навигации и форм;
- возможность собирать web-версию без отдельного React-приложения.

Ограничение: web-интерфейс должен учитывать особенности React Native Web, поэтому часть поведения viewport и оболочки приложения настраивается отдельно в `webapp/App.tsx`.

## React Query

React Query используется как клиентский слой управления серверным состоянием. Он отвечает за состояние загрузки, ошибки, повторное получение данных и обновление данных после мутаций.

Это разгружает компоненты экранов: они работают с результатами запросов и мутаций, а не реализуют собственную систему кэширования и синхронизации.

## JWT и серверные проверки прав

Авторизация построена на JWT. Клиент хранит токен и передает его в заголовке `Authorization`, а сервер извлекает пользователя через Passport и помещает его в tRPC-контекст.

Ключевое решение: права проверяются на сервере. Клиент может скрывать административные экраны или кнопки, но это только интерфейсное ограничение. Реальное разграничение доступа выполняется в серверных процедурах.

## Redis как опциональный кэш

Redis подключается только при наличии `REDIS_URL`. Это делает систему устойчивее в локальной разработке и упрощает запуск: базовая функциональность не зависит от кэша.

Такой подход подходит для дипломного проекта: можно показать возможность масштабирования и кэширования, не превращая Redis в обязательную точку отказа.

## Cloudinary для изображений

Изображения пользователей, сообществ и публикаций хранятся во внешнем сервисе Cloudinary. Сервер подготавливает параметры загрузки, а клиент загружает файл напрямую.

Преимущество решения: сервер не принимает тяжелые бинарные файлы на себя и не раскрывает клиенту секретные ключи Cloudinary.

## Sentry и Mixpanel

Sentry используется для фиксации неожиданных ошибок, Mixpanel - для аналитики клиентской навигации. Эти инструменты не являются частью основной бизнес-логики, но повышают наблюдаемость приложения.
